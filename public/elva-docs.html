Elva Devtools

把 Web 项目变成桌面应用，不用写一行构建配置

拖进一个项目文件夹 → 点「调试」本地跑起来 → 点「构建」拿到可分发产物。 Elva 是一个图形化的桌面应用开发工具，运行时契约沿用 Niva 生态，因此已有项目零改动可用。

Electron 44 Vue 3 129 个兼容 API 14 个运行时事件 macOS / Windows

这是什么

Elva 是「桌面应用运行时 + 图形化开发工作台」的组合。

129
兼容 API（14 个命名空间，逐名对齐）
14
运行时事件（窗口 / 菜单 / 托盘 / 快捷键 / 拖放 / 主题）
3
执行模型：同步 / 线程池限流 / 事件循环
0
老项目需要改动的代码行数

两个部件：

  • 兼容运行时（Electron 主进程）：实现一整套与 Niva 同形的 API、事件与 elva:// 自定义协议， 让按 Niva 契约写的网页能被当作桌面应用跑起来。
  • 工作台（Vue 3 渲染层）：项目列表、项目信息、配置编辑器，加上「调试 / 构建」两个动作。

Elva 不是 Niva

Elva 沿用 Niva 的接口契约（为了让老项目直接跑），但不是 Niva 的新版本、不做 Niva 的版本检测、 也不引导用户去下载 Niva。应用自身的版本、文档与品牌都是 Elva 自己的。

产品经理视角定位与目标用户

一句话：面向「已经有 Web 项目、想最快拿到桌面版」的开发者，把 Electron 的配置成本降到零。

要解决的问题

现状成本
手动配 Electron主进程 / preload / 打包配置 / 图标 / 签名，一套下来半天起步，且每个平台各一套
用 Tauri / Wails 等体积小但要学 Rust/Go，前端开发者上手门槛高
用现成壳工具多数只做「打包」，不做「本地调试闭环」——改一行代码要重新打包才能看到效果

目标用户

  • 主力用户：有 Vue / React / 原生 Web 项目的个人开发者，想把项目发成桌面版。
  • 次级用户：需要给内部工具做桌面客户端的小团队（不想为「一个壳」引入专门的客户端工程师）。
  • 非目标：需要精细控制主进程行为、需要原生模块深度集成的重型项目。

为什么是「调试 + 构建」两个动作

开发者的真实循环是「改代码 → 看效果 → 重复」，最后才是「出包」。所以产品只暴露两个按钮， 但把「调试」做成带热更新的本地窗口（指向 dev server），而不是一次性的打包预览。 构建则是把同一份配置固化成可分发产物。

产品经理视角与 niva 的关系与超越

策略：吸收契约，重做体验。接口层面兼容换来存量项目，体验层面重新做换增量用户。

继承的部分（有意保留，为了兼容）

  • 129 个 API 的方法名、参数顺序、返回结构、执行模型（同步 / 线程池 / 事件循环）逐名一致。
  • 14 个运行时事件的名称、载荷形态、派发时序一致，监听器签名仍是 (event, data)。
  • 配置文件格式（name / uuid / window / macos / windows …）与平台覆盖合并规则一致。
  • 注入 window.Niva，因此按原契约写的页面零改动可跑。

诚实说明：不照抄缺陷，但也不假装没有缺口

主进程运行时

  • runtime/context.js 读配置 → 生成 id_name（{name}_{uuid前8位}）→ 准备 data/cache/temp 目录。
  • runtime/api-manager.js 维护注册表，并按 三类执行模型 分派调用。
  • 各类 manager：窗口（windows.js）、菜单（menu.js）、托盘（tray.js）、快捷键（shortcut.js）。
  • runtime/api/*.js 按命名空间拆 14 个文件，api/index.js 是总注册表。
  • 自定义协议 elva:// 在 app.ready 之前声明为 privileged，再由 protocol.handle 提供资源。

preload 桥

  • 用 contextBridge 把兼容运行时注入主世界，因此页面里能直接写 Niva.api.xxx()，同时保留 contextIsolation。
  • 额外暴露自己的具名白名单 electronAPI（工作台专用：读应用信息、开外部链接、选文件），不做通用透传。
  • 拖放事件的绝对路径只能在渲染侧取到，这里用 webUtils.getPathForFile 解析后回传主进程。

渲染层

  • 工作台 UI（Vue 3 单文件组件，无 UI 框架依赖）：标题栏 / 状态栏 / 模态宿主 / 页面。
  • 状态层用 reactive + class 模型（models/*.js），与 React 版的 state-model 语义一一对应。

程序员视角兼容层契约

IPC 协议

渲染 → 主：[callbackId, "ns.method", args]；主 → 渲染：[callbackId, code, message, data]。

// 调用
Niva.call('window.setTitle', ['Hello'])
  → postMessage([12, "window.setTitle", ["Hello"]])

// 成功
[12, 0, "", null]

// 失败：code !== 0 时 reject 的是**整个数组**，不是 Error 对象
[12, 404, "window not found", null]

两个必须知道的细节

  • code !== 0 时 reject 的值是数组本身（[id, code, message, data]）， 所以调用方要判 Array.isArray(err) 才能取到 err[2] 里的消息。
  • 返回的 Promise 上额外挂了 .resolve / .reject，是原版的历史设计，保留以兼容。

三类执行模型

模型注册方式语义与适用
同步register_api 在事件循环里直接执行，立即返回。用于取值类轻操作（拿窗口尺寸、读配置）。
线程池register_async_api 投到固定大小（4）的并发池，超出的排队。用于文件 IO、网络、起子进程等会阻塞的操作。
事件循环register_event_api 抛回主循环执行，保证在主线程上与 UI 操作串行。用于关窗、开新窗口、退出等必须有序的动作。

执行模型是契约的一部分：同一个方法用错模型会导致时序问题（例如关窗抢在保存前执行）。 Elva 对 129 个方法逐一比对了模型归属，不只是名字对齐。

事件派发

一次 emit('window.focused', data) 会按三个 key 依次通知：

  1. window.focused（精确匹配）
  2. window.*（命名空间通配）
  3. *（全通配）

三条通知都是异步的（setTimeout(..., 0)），监听器签名统一 (event, data)。 因此「注册后同步检查命中数」必须为 0 —— 这本身就是一条可断言的契约。

程序员视角构建打包链路

macOS

  1. 准备目录结构（Contents/MacOS、Contents/Resources）。
  2. 复制可执行文件 —— elva 下复制的是 Electron 主可执行文件（Niva 下是它自己的原生运行时）。
  3. 打包资源：把项目目录按索引 + 数据块写进 RESOURCE_INDEXES / RESOURCE_DATA 两个具名资源段。
  4. 压缩：用浏览器原生 CompressionStream('deflate-raw')（不引 pako）。
  5. 生成 .icns 图标与 Info.plist。

Windows

  1. 准备构建目录，写入 VERSION_INFO（版本号会被拆成 4 段数字）。
  2. 用随包分发的辅助程序替换可执行文件的图标与版本信息段。
  3. 追加资源段，产出单个 .exe。

资源内嵌的形态

产物不是「exe + 一堆散落文件」，而是把前端资源压缩后塞进可执行文件的两个资源段。 运行时按索引随机读取，不必先解压到磁盘 —— 这是它能做到单文件分发的原因。

程序员视角启动性能

冷启动路径上做了三件事，都是可测量的。

1. 启动 IPC 并发化

原路径是三条串行 await，每条都要一次渲染进程 ↔ 主进程往返：

// 之前：三次往返串起来等
systemInfo = await Niva.api.os.info()
rawArgs    = await Niva.api.process.args()
await app.init()                     // 内部还有 history + locale 两次 IO

// 现在：一个往返的等待时间
const [info, rawArgs] = await Promise.all([
  Niva.api.os.info(),
  Niva.api.process.args(),
  app.init(),
])

用验收脚本实测「3 次串行」与「3 次并发」的往返耗时差，结果见 变更记录。

2. 构建层按需加载

build-macos / build-windows / templates 属于「点了构建才用」的代码， 改成动态 import() 后从首屏 bundle 里拆了出去：

// 构建产物里能看到它们成了独立 chunk
dist/assets/build-macos-*.js      1.47 kB
dist/assets/build-windows-*.js    1.89 kB
dist/assets/base-*.js             1.02 kB
dist/assets/index-*.js          109.18 kB   ← 首屏

3. 消除白闪

窗口创建时指定 backgroundColor 与页面背景一致，避免「先白屏再渲染」的闪一下。 窗口尺寸也改为可缩放（带最小尺寸），而不是原版的固定尺寸。

4. 历史与语言并发初始化

app.init() 内部把「读历史文件」与「读系统语言」由串行改为 Promise.all。

程序员视角扩展点

加一个兼容 API

  1. 在 electron/runtime/api/<命名空间>.js 里按模型选 register / registerAsync / registerEvent。
  2. 用 arg(args, i) / optional(args, i) 取值，保持参数校验风格一致。
  3. 在 api/index.js 的 registerAll 里挂上（注册顺序会影响 window.list() 的输出次序）。
  4. 跑 tools/verify/elva-dump-apis.js 导出运行时注册表，与 tools/audit/collect-niva-apis.py 抽出的原版名单做逐名 diff。

加一个新页面

  1. 组件放 src/components/devtools/，样式写进 src/assets/devtools/pages.css（无 sass，扁平选择器）。
  2. 文案先加进 src/devtools/i18n.js 的 en_US 与 zh_CN，再通过 locale.t('KEY') 取。
  3. 挂快捷键：在 composables/useShortcuts.js 的 SHORTCUT 里加常量与键位，组件内用 onShortcut({...}) 订阅。

加一个事件

主进程侧用 emitToWindow(nivaWindow, 'ns.name', payload)，渲染侧用 Niva.addEventListener('ns.name', (event, data) => {}) 监听。三个 key 的派发规则由 runtime/events.js 统一处理，不需要各调用点重复。

程序员视角能力边界

这些是 Electron 本身做不到或做法不同的，不假装已对齐。

能力原版行为elva 现状
window.setDecorated macOS 支持运行时开关窗口装饰 无对应 API —— 保留注册、不抛异常、返回类型合法；首次调用告警一次
编程式拖动窗口 dragWindow() 走原生 drag_window 改由 CSS -webkit-app-region: drag 承担；API 仍保留可调用

降级的统一原则：保留方法存在性 + 返回类型合法 + 不抛异常 + 首次调用告警。 因为调用方拿到「方法不存在」比「功能缺失」更偏离契约。

用户视角快速上手

  1. 导入项目：把项目文件夹拖进窗口，或点「选择项目」定位。 如果目录里没有配置文件，Elva 会问你要不要创建 —— 选「确认」即可，它会根据 package.json 猜出项目类型（React / Vue / Vite / 纯静态）并生成一份带合理默认值的配置。
  2. 调试：切到「项目配置」核对 debug.entry（前端 dev server 地址）与 debug.resource，然后点「调试」。会另起一个窗口加载你的页面，改动照常热更新。
  3. 构建：点「构建」，选择输出路径。进度条会逐阶段汇报，完成后自动打开产物所在目录。

左侧列表就是你的项目历史，点一下即可切换；hover 出现删除图标，删除有二次确认。

用户视角常见问题

我的项目里是 niva.json，需要改名吗？

不需要。Elva 优先读 elva.json，找不到就自动回退读 niva.json。 新建项目时会生成 elva.json；两者同时存在时以 elva.json 为准。

点「调试」没反应 / 窗口一片白？

多半是 debug.entry 指的前端服务没起来。先在项目目录里把 dev server 跑起来， 确认 http://127.0.0.1:端口 能打开，再回 Elva 点调试。

构建失败怎么办？

看进度条停在哪一步 —— 阶段名就是失败位置。常见三类：

  • 准备构建环境失败：输出目录没有写权限，或路径里有特殊字符。
  • 打包 / 压缩资源失败：资源目录里有读不到的文件（权限或损坏的软链接）。
  • 生成图标失败：图标不是合法的 PNG，或尺寸不是正方形。

为什么 macOS 上的窗口按钮和别人的不一样？

因为用的是系统原生那套 —— 左上角的红黄绿圆点就是 macOS 自己的按钮，位置和行为都由系统负责， 所以看起来跟所有正规 mac 应用一致。Windows 上因为窗口是无边框的，没有系统按钮，才由 Elva 自绘。

状态栏右边那串是什么？

系统信息 + 版本号：Mac OS arm64 | Elva 0.1.0 | Electron 44.x。 单击复制到剪贴板（反馈问题时报这个最有用），双击打开开发者工具。

怎么确认它在用我的配置文件？

切到「项目配置」tab，标题栏带红星号说明有未保存修改；「项目信息」里的「配置文件」一行显示的就是实际读取的文件路径。
